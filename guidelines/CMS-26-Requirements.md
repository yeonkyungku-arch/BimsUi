# CMS-26 기능별 요청사항 및 수정 내역

---

## CMS-26-001 | 언어 설정(변경)
> 글로벌 버전 개발 | 계정 정보(회원정보) | 우선순위: highest

### 요청사항
프로필에서 언어(ko/en)를 선택하면 서비스 UI 언어가 변경되고, 이메일/알림 및 리포트(다운로드/PDF) 문구까지 동일 언어로 표시되어야 한다.

### 요청한 이유
글로벌 서비스 확장으로 영어권 사용자가 유입될 예정이며, 현재 한국어만 지원되어 해외 사용자가 서비스를 이용할 수 없다. 단순 UI 번역을 넘어 이메일·알림·리포트 등 모든 접점에서 일관된 언어 경험이 필요하다.

### 수정사항
- 프로필 > 설정 화면에 언어 선택(ko/en) UI 추가
- languageCode 기반으로 서비스 전체 UI 언어 전환 적용
- 이메일/알림 발송 시 사용자 languageCode에 맞는 템플릿 사용
- 리포트(다운로드/PDF) 생성 시 languageCode 기반 문구 적용
- 미지원 코드 입력 시 ko fallback, 번역 키 누락 시 기본 언어 표시

### 이렇게 수정한 이유
다국어 적용 범위를 UI·이메일·알림·리포트 전 영역으로 확대하여 어떤 접점에서도 동일 언어 경험을 제공한다. 허용값을 ko/en으로 제한하고 fallback을 ko로 설정하여 예상치 못한 언어 코드로 인한 UI 깨짐을 방지한다.

## CMS-26-002 | 언어 설정 유지
> 글로벌 버전 개발 | 계정 정보(회원정보) | 우선순위: highest

### 요청사항
사용자가 설정한 언어를 프로필에 저장하여 재로그인 후에도 동일 언어가 유지되어야 한다.

### 요청한 이유
언어를 설정하더라도 로그아웃 후 재로그인 시 초기화되면 매번 재설정해야 하는 불편함이 생긴다. 다중 기기·브라우저 환경에서도 설정한 언어가 유지되어야 실용적인 다국어 서비스가 된다.

### 수정사항
- languageCode를 사용자 프로필 DB에 저장
- 로그인 시 저장된 languageCode 우선 적용, 미설정 시 ko 기본값
- 저장값 손상 또는 미지원 코드인 경우 ko로 자동 적용

### 이렇게 수정한 이유
언어 설정을 브라우저 로컬 스토리지가 아닌 서버 DB에 저장하여 다중 기기에서도 일관된 언어를 유지한다. 언어코드(languageCode)로 관리하여 이후 추가 언어 지원 시 확장이 용이하다.

## CMS-26-003 | 회원정보-국가 선택 추가
> 글로벌 버전 개발 | 계정 정보(회원정보) | 우선순위: highest

### 요청사항
회원가입/회원정보 수정 시 국가 선택 필드를 추가하고 저장해야 한다. 해당 값은 전화번호·식별번호 입력 규칙의 기준값으로 활용된다.

### 요청한 이유
전화번호 및 사업자번호 입력 형식이 한국 기준으로 고정되어 있어 해외 사용자는 자국 번호 형식을 입력할 수 없다. 국가 코드를 기준값으로 삼아야 각 국가에 맞는 입력 검증 규칙을 적용할 수 있다.

### 수정사항
- 회원가입 및 프로필 > 회원정보 수정 화면에 국가 선택(countryCode) 필드 추가
- 필수 입력, 허용 국가 리스트 내 값만 선택 가능
- 미선택 또는 허용값 외 입력 시 오류 처리
- 허용 국가 리스트업 별도 작업 필요

### 이렇게 수정한 이유
국가 선택을 독립 필드로 분리하여 전화번호·사업자번호 등 후속 입력 필드의 유효성 검증 기준으로 활용한다. 허용 국가 리스트로 범위를 제한하여 미지원 국가로 인한 예외 상황을 사전에 차단한다.

## CMS-26-004 | 회원정보-전화번호 입력 유연화
> 글로벌 버전 개발 | 계정 정보(회원정보) | 우선순위: high

### 요청사항
전화번호 입력 구조를 유연화하고 국가별 검증 규칙을 적용할 수 있는 구조로 개선해야 한다.

### 요청한 이유
현재 전화번호 입력이 한국 번호 형식(010-xxxx-xxxx)에 고정되어 있어 해외 전화번호를 입력·저장할 수 없다. 글로벌 사용자 대응을 위해 국가별 번호 형식을 수용하는 구조가 필요하다.

### 수정사항
- countryCode 선행 입력 후 해당 국가 기준으로 전화번호 유효성 검증 적용
- 국가별 검증 정책을 별도 정책 문서로 관리
- 형식 오류 시 안내 메시지 표시
- 저장 표준(E.164 등) 정책 추가 논의 필요 (TBD)

### 이렇게 수정한 이유
E.164 등 국제 표준 저장 방식을 검토하여 DB에는 표준화 형식으로 저장하고 화면에는 국가별 포맷으로 표시하는 방식을 기준으로 삼는다. countryCode 선행 입력으로 전화번호 검증 규칙을 동적으로 적용하여 국가 추가 시 코드 변경 없이 확장할 수 있다.

## CMS-26-005 | 회원정보-사업자/식별번호 구조 개편
> 글로벌 버전 개발 | 계정 정보(회원정보) | 우선순위: highest

### 요청사항
고정된 3-2-5 입력 형식을 제거하고 유연한 단일 입력 필드를 적용해야 한다.

### 요청한 이유
사업자등록번호 입력이 한국 형식(XXX-XX-XXXXX)으로 고정되어 해외 사업자번호 또는 식별번호를 입력할 수 없다. 국가마다 식별번호 형식이 달라 자유 입력 구조가 필요하다.

### 수정사항
- 미디어사(corpNum), 광고회사(adCompanyCorpNum) 입력을 3-2-5 형식에서 단일 자유 입력 필드로 전환 (필수 진행)
- 기존 데이터 마이그레이션은 권장 사항(우선순위 Medium)
- 입력값 인증 정책은 추후 논의 필요 (TBD)

### 이렇게 수정한 이유
각국의 사업자/식별번호 자릿수와 형식이 다르므로 고정 형식을 유지하면 해외 번호를 수용할 수 없다. 단일 자유 입력 필드로 전환하여 구조적 확장성을 확보하고, 입력값 인증은 정책 논의 후 별도 검증 로직으로 추가한다.

## CMS-26-006 | 회원정보-레거시 데이터 마이그레이션
> 글로벌 버전 개발 | 계정 정보(회원정보) | 우선순위: medium

### 요청사항
기존 저장된 전화/사업자/식별번호 데이터를 신규 구조로 변환·정리해야 한다.

### 요청한 이유
CMS-26-004, CMS-26-005에서 입력 구조가 변경되면 기존 DB 데이터가 신규 구조와 불일치한다. 기존 데이터를 신규 구조로 변환해야 서비스 일관성이 유지된다.

### 수정사항
- 기존 3-2-5 형식 사업자번호를 단일 필드 형식으로 변환
- 기존 전화번호 데이터를 확정된 표준(E.164 등)에 맞게 정리
- 마이그레이션 스크립트 작성 및 실행

### 이렇게 수정한 이유
입력 구조 전환(CMS-26-005)은 필수이나 데이터 마이그레이션은 우선순위 Medium으로 분류하여 신규 구조 적용 이후 별도 일정으로 진행한다. 마이그레이션 전 데이터 검증 단계를 포함하여 변환 오류를 최소화한다.

## CMS-26-007 | 미디어그룹 운영시간 타임존 반영
> 글로벌 버전 개발 | 미디어그룹 | 우선순위: highest

### 요청사항
미디어그룹 생성/수정 시 국가/타임존을 지정하고 해당 타임존 기반으로 운영시간을 설정·표시해야 한다. DST(일광절약시간제)도 초기부터 대응한다.

### 요청한 이유
운영시간이 서버 기준(한국 시간)으로만 저장·표시되어 해외 거점 미디어그룹의 현지 실제 운영시간과 불일치가 발생한다.

### 수정사항
- 미디어그룹 생성/수정 화면에 타임존(또는 countryCode) 선택 필드 추가
- operateFromTime/operateToTime, operateDay를 지정 타임존 기준으로 저장 및 표시
- DST 구간 시간 중복/누락 처리 정책 수립 (TBD)
- 운영시간 적용 방식 확인 필요: 서버에서 타임존 계산 후 전송하는 방식인지, 안드로이드 셋탑이 현지 시간 기준으로 자체 적용하는 방식인지 확인 후 구현

### 이렇게 수정한 이유
운영시간 코드(operateFromTime/operateToTime)와 요일(operateDay)은 기존 필드를 유지하고 타임존 정보만 추가하여 구조 변경을 최소화한다. DST를 초기부터 고려하여 서머타임 적용 국가에서 발생할 운영시간 오류를 사전에 방지한다.

## CMS-26-008 | IR 센서 데이터 수집 구조/API
> 글로벌 버전 개발 | 데이터 수집/분석 | 우선순위: highest

### 요청사항
IR 센서 데이터를 수집·저장하고 수집 API를 구성해야 한다.

### 요청한 이유
시청자 반응 데이터를 수집하여 광고 효과 분석에 활용하려면 IR 센서로부터 데이터를 수신·저장하는 인프라가 필요하다. 현재 수집 구조 및 API가 없어 센서 데이터 활용이 불가능하다.

### 수정사항
- IR 센서 데이터 수집 API 구성 (deviceId, sensorId, eventTime, value/count, meta 필수)
- 필수값 누락 금지, 포맷 고정(정책 수립 필요)
- 중복 적재, 비정상값, 유실 재전송 처리 정책 수립
- 운영 수집 현황/로그 화면 기획 필요 (TBD)
- 데이터 표준화 정책 및 저장/처리 용량 확보 필요

### 이렇게 수정한 이유
데이터 표준화 정책을 선행하여 향후 다양한 센서 유형이 추가되어도 동일 API 구조로 수집할 수 있도록 확장성을 확보한다. 중복 적재 방지 및 재전송 처리 정책을 명시하여 데이터 무결성을 보장한다.

## CMS-26-009 | ColorLight LED 셋탑 전용 앱 기본 골격
> 서비스 시장 확장 | App | 우선순위: highest

### 요청사항
ColorLight LED 셋탑에서 앱 설치·실행이 가능한 기본 앱(권한/네트워크/저장소 포함)을 구축해야 한다.

### 요청한 이유
기존 앱은 Quber 셋탑 전용으로 ColorLight LED 셋탑에서 동작하지 않는다. ColorLight 하드웨어 파트너사와의 협업 및 새로운 시장 진출을 위해 전용 앱 기반이 필요하다.

### 수정사항
- ColorLight LED 셋탑 지원 OS/스펙 확보
- 권한, 네트워크, 저장소 구조를 포함한 기본 앱 골격 구축
- 설치/실행 실패 시 사용자 안내 처리
- 배포 방식(OTA 포함) 추후 확정 (TBD)

### 이렇게 수정한 이유
완전 신규 개발보다 기존 Quber 앱 소스에서 CMS-26-010(의존 기능 목록화) 결과를 기반으로 ColorLight에 맞게 포팅하여 개발 기간을 단축한다. 기본 골격을 먼저 구축하고 기능별로 단계적으로 구현하여 위험을 분산한다.

## CMS-26-010 | ColorLight LED 셋탑-의존 기능 목록화
> 서비스 시장 확장 | App | 우선순위: highest

### 요청사항
기존 소스의 의존 기능을 목록화하고 동등/대체/미지원 여부를 분류하여 ColorLight 대응 범위를 확정해야 한다.

### 요청한 이유
ColorLight 앱 개발 전 기존 Quber 앱 기능 중 어떤 것이 그대로 사용 가능하고, 어떤 것이 대체가 필요하거나 지원 불가한지 파악해야 개발 일정과 리소스를 정확히 산정할 수 있다.

### 수정사항
- 기존 Quber 앱 전체 기능 목록 작성
- 각 기능에 대해 ColorLight 동등 지원 / 대체 구현 필요 / 미지원 분류
- 필수/선택 기능 구분하여 개발 우선순위 확정
- 산출물(목록 문서) 필수 제출

### 이렇게 수정한 이유
의존 기능 목록화를 CMS-26-009(기본 골격 구축)와 병행하여 기본 앱 구축과 동시에 범위를 확정한다. 미지원 기능은 사용자 안내나 대체 UI로 처리하여 기능 누락으로 인한 운영 혼란을 방지한다.

## CMS-26-011 | ColorLight LED 셋탑-콘텐츠+스케줄 재생 호환
> 서비스 시장 확장 | App | 우선순위: highest

### 요청사항
콘텐츠가 ColorLight에서 정상 재생되도록 플레이어/렌더링을 구현해야 한다. 스케줄 수신→적용→재생(순서/시간)을 지원하며 즉시반영도 포함한다.

### 요청한 이유
ColorLight LED 셋탑은 Quber와 하드웨어 구조가 달라 기존 플레이어로는 콘텐츠가 정상 재생되지 않을 수 있다. 셋탑의 핵심 기능인 콘텐츠 재생 및 스케줄 적용이 정상 동작해야 서비스 제공이 가능하다.

### 수정사항
- ColorLight 하드웨어에 맞는 플레이어/렌더링 구현
- 지원 콘텐츠 포맷 확정 (TBD) 및 유효성 검증 적용
- 스케줄 수신 → 파싱 → 순서/시간에 따라 재생하는 전체 플로우 구현

### 이렇게 수정한 이유

### 요청사항
'재생로그(상세)' 탭에서 선택 기간 동안의 재생 이벤트를 건별로 조회 및 다운로드할 수 있어야 한다. 무한 스크롤로 탐색하며, 각 이벤트는 콘텐츠 식별 정보와 송출 시각을 포함해야 한다.

### 요청한 이유
광고 운영 검증이나 이슈 분석 시 개별 재생 이벤트 수준의 로그가 필요하지만 현재는 집계 수치만 제공된다. 건별 재생 이력 추적이 가능해야 광고 송출 보증 및 분쟁 처리가 가능하다.

### 수정사항
- 재생로그(상세) 탭에서 dateRange, mediaId/deviceId, contentId 기반 이벤트 목록 무한 스크롤 조회
- 각 이벤트에 콘텐츠 식별 정보 + 송출 시각 필수 포함
- 최대 조회 기간 제한 정책 수립
- 대용량 조회 시 로딩/부분 로딩 처리
- 데이터 없음/조회 실패 상태 처리
- 다운로드 기능 제공

### 이렇게 수정한 이유
무한 스크롤 방식으로 대용량 로그를 페이지 분할 없이 탐색할 수 있도록 하며, 최대 조회 기간 제한으로 서버 부하를 관리한다. 다운로드 기능으로 오프라인 분석 및 보고 자료 작성에 활용할 수 있도록 한다.

## CMS-26-048 | 다중 선택 UX 제공
> 서비스 고도화 | 공통 리스트 | 우선순위: medium

### 요청사항
리스트 화면에서 다중 선택 후 일괄 삭제 및 복제 기능을 제공해야 한다.

### 요청한 이유
콘텐츠·스케줄·미디어 등이 많은 환경에서 개별 항목을 하나씩 처리하는 작업이 비효율적이다.

### 수정사항
- 리스트 화면에 체크박스 기반 다중 선택 UI 추가
- selectedIds 1개 이상 선택 가능
- 선택 0개 상태에서 액션 실행 제한
- 조건 미충족 대상(예: 운영중 스케줄) 선택 불가 처리
- 기본 동작(전체선택/필터 변경 시 선택 유지) 정책 확정 필요

### 이렇게 수정한 이유

## CMS-26-049 | 일괄 삭제/복제 액션 제공
> 서비스 고도화 | 공통 리스트 | 우선순위: medium

### 요청사항
리스트 화면에 체크박스 기반 다중 선택 기능을 제공하여 여러 항목을 한 번에 선택하고 일괄 처리할 수 있어야 한다. 전체 선택/선택 해제, 선택 개수 표시 등 기본 UX를 포함한다.

### 요청한 이유
일괄 삭제·복제 기능을 제공하더라도 한 번에 여러 항목을 선택하는 UX가 없으면 개별 선택-처리를 반복해야 한다. 다중 선택 UX를 표준화하여 모든 리스트 화면에서 일관된 방식으로 제공해야 한다.

### 수정사항
- selectedIds, action(delete/copy) 기반 일괄 처리
- 선택 항목 1개 이상 조건 검증
- 삭제·복제 조건(운영중 등) 검증 후 처리 차단/안내
- 부분 실패 시 성공/실패 목록 구분 안내
- 삭제 불가 상태는 CMS-26-029(Soft/Hard Delete 정책)에 따라 처리

### 이렇게 수정한 이유
부분 실패를 명시적으로 처리하여 어떤 항목이 처리됐고 어떤 항목이 실패했는지 사용자가 정확히 파악할 수 있도록 한다. 삭제 정책(CMS-26-029)과 연계하여 일관된 삭제 동작을 보장한다.

## CMS-26-050 | 대시보드 그래프 인터랙션 개선

### 요청사항

## CMS-26-051 | 플로팅 버튼 제공 로직 개선
> 서비스 고도화 | 공통 | 우선순위: low

### 요청사항
플로팅 버튼 노출/비노출 조건과 동작 로직을 개선하여 화면 상태에 따라 일관되게 제공되어야 한다(중복 노출/오작동 방지).

### 요청한 이유
플로팅 버튼이 화면 상태와 무관하게 노출되거나 중복으로 표시되는 등 일관되지 않은 동작이 보고되었다. 잘못된 컨텍스트에서 노출되면 의도하지 않은 액션이 실행될 수 있다.

### 수정사항
- 페이지/권한/스크롤/상태 기반 노출 조건 정의
- 노출 조건 및 버튼 액션 정의 완료 후 구현
- 중복 노출 방지 로직 추가
- 대시보드/공통 영역 전반에 적용

### 이렇게 수정한 이유
노출 조건을 명확히 정의한 후 구현하여 화면 상태에 따라 일관된 플로팅 버튼 동작을 보장한다. 중복 노출 방지 로직을 공통 컴포넌트 수준에서 처리하여 각 화면에서 개별 관리 없이 일관성을 유지한다.
