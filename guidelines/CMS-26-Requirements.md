## CMS-26-009 | ColorLight LED 셋탑 전용 앱 기본 골격
> 서비스 시장 확장 | App | 우선순위: highest

### 요청사항
- ColorLight LED 셋탑에서 설치·실행 가능한 전용 앱 구축
- 권한·네트워크·저장소 포함한 기본 골격 구성

### 요청한 이유
- 새로운 시장 진출을 위해 ColorLight 셋탑 활용 필요
- 기존 앱이 해당 셋탑을 미지원하여 서비스 자체 불가

### 수정사항
- ColorLight LED 셋탑 지원 OS/스펙 확보
- 권한, 네트워크, 저장소 구조를 포함한 기본 앱 골격 구축
- 설치/실행 실패 시 사용자 안내 처리
- 배포 방식(OTA 포함) 추후 확정 (TBD)

### 이렇게 수정한 이유
- 기본 골격 단계에서 실패 안내 포함 시 문제 상황 대처 가능
- 기능별 단계적 구현으로 개발 위험 분산

## CMS-26-010 | ColorLight LED 셋탑-의존 기능 목록화
> 서비스 시장 확장 | App | 우선순위: highest

### 요청사항
- 기존 앱 기능의 ColorLight 동등 지원·대체 필요·미지원 여부 분류 및 목록화

### 요청한 이유
- 지원 가능 기능과 신규 개발 필요 기능 파악 없이 일정·범위 예측 불가
- 사업 계획 수립을 위한 기능 범위 확정 필요

### 수정사항
- 기존 Quber 앱 전체 기능 목록 작성
- 각 기능에 대해 ColorLight 동등 지원 / 대체 구현 필요 / 미지원 분류
- 필수/선택 기능 구분하여 개발 우선순위 확정
- 산출물(목록 문서) 필수 제출

### 이렇게 수정한 이유
- 미지원 기능 명확 분류로 UI에서 적절히 안내, 사용자 혼란 방지
- 목록화 결과 기반으로 개발 우선순위 확정

## CMS-26-011 | ColorLight LED 셋탑-콘텐츠+스케줄 재생 호환
> 서비스 시장 확장 | App | 우선순위: highest

### 요청사항
- ColorLight 셋탑에서 콘텐츠 정상 재생
- 스케줄에 따른 순서·시간 기반 송출 및 즉시반영 지원

### 요청한 이유
- ColorLight 셋탑은 Quber와 하드웨어 구조가 달라 기존 플레이어로 재생 불가
- 재생·스케줄 적용 동작 없이는 실제 서비스 불가

### 수정사항
- ColorLight 하드웨어에 맞는 플레이어/렌더링 구현
- 지원 콘텐츠 포맷 확정 (TBD) 및 유효성 검증 적용
- 스케줄 수신 → 파싱 → 순서/시간에 따라 재생하는 전체 플로우 구현
- 즉시반영 명령 수신 시 신규 스케줄로 전환
- 재생 실패 시 로그 기록 및 재시도 정책 수립 (TBD)

### 이렇게 수정한 이유
- 재생 실패 시 명확한 로그·상태 표시로 원인 파악 동선 단축
- 재시도 정책으로 일시적 오류로 인한 재생 중단 최소화

- CMS-26-009(기본 골격)와 연계하여 구현

### 이렇게 수정한 이유
- 명령 결과를 운영로그에 즉시 표시하여 화면 안에서 확인 완결

## CMS-26-015 | LG 여부 필드 추가
> 서비스 시장 확장 | 미디어 | 우선순위: high

### 요청사항
- 미디어 정보에 LG 디스플레이 여부(isLgDisplay) 필드 추가

### 요청한 이유
- LG 전용 모니터링·제어 기능 제공을 위해 LG 여부 식별 필요
- 현재 디스플레이 제조사 구분 필드 없어 식별 불가

### 수정사항
- 미디어 등록/수정 화면에 isLgDisplay(불린) 필드 추가
- 유효한 불린값(true/false)만 허용
- 저장 실패 시 오류 안내

### 이렇게 수정한 이유
- isLgDisplay 필드로 불필요한 옵션 숨기고 관련 사용자에게만 기능 노출
- 화면 복잡도 감소 및 조건부 렌더링 기준값으로 활용

## CMS-26-016 | LG 전용 모니터링 노출
> 서비스 시장 확장 | 모니터링 | 우선순위: high

### 요청사항
- LG 디스플레이 미디어 상세 화면에 LG 전용 모니터링 항목 표시

### 요청한 이유

- 상태 데이터 미수신 시 안내 메시지 표시

### 이렇게 수정한 이유
- LG 미사용자 화면에 전용 항목 노출 시 불필요한 혼란 유발
- 조건부 렌더링으로 관련 사용자에게만 필요한 정보 표시

## CMS-26-019 | Gateway 명령 전송 안정화(중복제거/재전송)
> 서비스 고도화 | Gateway | 우선순위: highest

### 요청사항
- 서버→디바이스 제어 명령 유실·중복 전송 문제 해결
- 명령 수신 확인 + 적용 완료의 2단계 ACK 구성

### 요청한 이유
- 중요 제어 명령(즉시반영·재부팅) 실패 시 CMS에서 확인 방법 없음
- 실패 확인을 위해 현장 별도 연락 필요한 상황

### 수정사항
- Gateway를 서버와 디바이스 사이에 배치하여 명령 중계 역할 담당
- 대상/명령유형 기준으로 중복 명령 판단 및 제거
- 무응답 시 재전송 (타임아웃/횟수 정책 TBD)
- ACK를 2단계(수신 확인 + 적용 완료)로 관리
- 최종 실패 처리 정책 수립
- 모니터링 > 디바이스 상세 > 제어/명령에서 상태 확인 가능

### 이렇게 수정한 이유
- ACK 2단계로 "수신됨/적용 완료" 세밀한 상태 추적 가능
- 사용자가 제어 결과를 화면에서 실시간으로 파악, 불안 경험 제거

- 표기 규칙(단위/반올림/소수점) 정책 확정 후 일관 적용 (TBD)

- 다중 선택 후 일괄 삭제·복제 처리 기능 제공
- 부분 실패 시 성공·실패 목록 구분 안내

### 요청한 이유
- 유사 광고 설정 반복 생성·대량 정리 시 항목별 개별 처리로 비효율적
- 빠른 일괄 처리 기능 필요

- selectedIds, action(delete/copy) 기반 일괄 처리
- 선택 항목 1개 이상 조건 검증
- 삭제·복제 조건(운영중 등) 검증 후 처리 차단/안내

- 삭제 불가 상태는 CMS-26-029(Soft/Hard Delete 정책)에 따라 처리

- 부분 실패 명시적 처리로 실패 항목만 빠르게 재처리, 후속 작업 부담 감소

## CMS-26-053 | 반응형 UI 지원
> 서비스 고도화 | 공통 | 우선순위: medium

### 요청사항
- CMS 화면 전체를 다양한 디바이스(데스크탑·태블릿·모바일) 해상도에 맞게 반응형으로 지원

### 요청한 이유
- 현재 CMS가 고정 레이아웃으로 구성되어 태블릿·모바일 환경에서 화면 깨짐 및 사용 불편 발생
- 현장 방문 시 모바일로 CMS를 확인·조작해야 하는 상황 발생

### 수정사항
- 화면 너비 기준 브레이크포인트 정책 확정 (데스크탑/태블릿/모바일)
- 공통 레이아웃(헤더·사이드바·콘텐츠 영역) 반응형 구조로 전환
- 테이블·폼·모달 등 주요 컴포넌트 반응형 처리
- 터치 인터랙션(스와이프·탭) 지원 정책 확정 (TBD)

### 이렇게 수정한 이유
- 반응형 지원으로 디바이스 제약 없이 CMS 접근 가능, 현장 운영 효율 향상
- 고정 레이아웃 깨짐으로 인한 데이터 오확인·오조작 위험 제거
