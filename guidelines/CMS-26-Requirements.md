# CMS-26 기능별 요청사항 및 수정 내역

---

## CMS-26-001 | 언어 설정(변경)
> 글로벌 버전 개발 | 계정 정보(회원정보) | 우선순위: highest

### 요청사항
프로필에서 언어(ko/en)를 선택하면 서비스 UI 언어가 변경되고, 이메일/알림 및 리포트(다운로드/PDF) 문구까지 동일 언어로 표시되어야 한다.

### 요청한 이유
글로벌 서비스 확장으로 영어권 사용자가 유입될 예정이며, 현재 한국어만 지원되어 해외 사용자가 서비스를 이용할 수 없다. 단순 UI 번역을 넘어 이메일·알림·리포트 등 모든 접점에서 일관된 언어 경험이 필요하다.

### 수정사항
- 프로필 > 설정 화면에 언어 선택(ko/en) UI 추가
- languageCode 기반으로 서비스 전체 UI 언어 전환 적용
- 이메일/알림 발송 시 사용자 languageCode에 맞는 템플릿 사용
- 리포트(다운로드/PDF) 생성 시 languageCode 기반 문구 적용
- 미지원 코드 입력 시 ko fallback, 번역 키 누락 시 기본 언어 표시

### 이렇게 수정한 이유
사용자가 선택한 언어가 UI에만 적용되고 이메일·알림에서는 다른 언어로 나오면 인지 일관성이 깨져 혼란을 준다. 모든 접점에서 동일 언어를 유지하여 사용자가 "내 설정이 제대로 반영됐다"는 신뢰감을 가질 수 있도록 한다.

## CMS-26-002 | 언어 설정 유지
> 글로벌 버전 개발 | 계정 정보(회원정보) | 우선순위: highest

### 요청사항
사용자가 설정한 언어를 프로필에 저장하여 재로그인 후에도 동일 언어가 유지되어야 한다.

### 요청한 이유
언어를 설정하더라도 로그아웃 후 재로그인 시 초기화되면 매번 재설정해야 하는 불편함이 생긴다. 다중 기기·브라우저 환경에서도 설정한 언어가 유지되어야 실용적인 다국어 서비스가 된다.

### 수정사항
- languageCode를 사용자 프로필 DB에 저장
- 로그인 시 저장된 languageCode 우선 적용, 미설정 시 ko 기본값
- 저장값 손상 또는 미지원 코드인 경우 ko로 자동 적용

### 이렇게 수정한 이유
로그인할 때마다 언어를 다시 설정해야 한다면 사용자는 반복 작업을 강요받는 느낌을 받는다. 설정을 기억해주는 것은 "시스템이 나를 알아본다"는 경험을 주어 서비스 신뢰도를 높인다.

## CMS-26-003 | 회원정보-국가 선택 추가
> 글로벌 버전 개발 | 계정 정보(회원정보) | 우선순위: highest

### 요청사항
회원가입/회원정보 수정 시 국가 선택 필드를 추가하고 저장해야 한다. 해당 값은 전화번호·식별번호 입력 규칙의 기준값으로 활용된다.

### 요청한 이유
전화번호 및 사업자번호 입력 형식이 한국 기준으로 고정되어 있어 해외 사용자는 자국 번호 형식을 입력할 수 없다. 국가 코드를 기준값으로 삼아야 각 국가에 맞는 입력 검증 규칙을 적용할 수 있다.

### 수정사항
- 회원가입 및 프로필 > 회원정보 수정 화면에 국가 선택(countryCode) 필드 추가
- 필수 입력, 허용 국가 리스트 내 값만 선택 가능
- 미선택 또는 허용값 외 입력 시 오류 처리
- 허용 국가 리스트업 별도 작업 필요

### 이렇게 수정한 이유
국가를 먼저 선택하면 이후 전화번호·식별번호 입력 필드가 해당 국가 기준으로 바뀐다. 이는 사용자가 "어떻게 입력해야 하나"를 추측하는 인지 부담을 없애고, 입력 전에 기대 형식을 예측할 수 있게 해준다.

## CMS-26-004 | 회원정보-전화번호 입력 유연화
> 글로벌 버전 개발 | 계정 정보(회원정보) | 우선순위: high

### 요청사항
전화번호 입력 구조를 유연화하고 국가별 검증 규칙을 적용할 수 있는 구조로 개선해야 한다.

### 요청한 이유
현재 전화번호 입력이 한국 번호 형식(010-xxxx-xxxx)에 고정되어 있어 해외 전화번호를 입력·저장할 수 없다. 글로벌 사용자 대응을 위해 국가별 번호 형식을 수용하는 구조가 필요하다.

### 수정사항
- countryCode 선행 입력 후 해당 국가 기준으로 전화번호 유효성 검증 적용
- 국가별 검증 정책을 별도 정책 문서로 관리
- 형식 오류 시 안내 메시지 표시
- 저장 표준(E.164 등) 정책 추가 논의 필요 (TBD)

### 이렇게 수정한 이유
고정된 형식 마스크(예: 010-xxxx-xxxx)가 있으면 해외 번호를 입력하는 사용자는 입력 자체가 막히는 경험을 한다. 자국 번호를 자연스럽게 입력할 수 있게 해야 "이 서비스가 나를 위한 것"이라고 느낄 수 있다.

## CMS-26-005 | 회원정보-사업자/식별번호 구조 개편
> 글로벌 버전 개발 | 계정 정보(회원정보) | 우선순위: highest

### 요청사항
고정된 3-2-5 입력 형식을 제거하고 유연한 단일 입력 필드를 적용해야 한다.

### 요청한 이유
사업자등록번호 입력이 한국 형식(XXX-XX-XXXXX)으로 고정되어 해외 사업자번호 또는 식별번호를 입력할 수 없다. 국가마다 식별번호 형식이 달라 자유 입력 구조가 필요하다.

### 수정사항
- 미디어사(corpNum), 광고회사(adCompanyCorpNum) 입력을 3-2-5 형식에서 단일 자유 입력 필드로 전환 (필수 진행)
- 기존 데이터 마이그레이션은 권장 사항(우선순위 Medium)
- 입력값 인증 정책은 추후 논의 필요 (TBD)

### 이렇게 수정한 이유
3-2-5 고정 형식은 한국 사용자에게는 익숙하지만 해외 사용자에게는 완전히 낯선 제약이다. 자유 입력 필드로 전환하면 입력 방법을 알아내야 하는 부담이 사라지고 누구든 자신의 번호를 막힘 없이 입력할 수 있다.

## CMS-26-006 | 회원정보-레거시 데이터 마이그레이션
> 글로벌 버전 개발 | 계정 정보(회원정보) | 우선순위: medium

### 요청사항
기존 저장된 전화/사업자/식별번호 데이터를 신규 구조로 변환·정리해야 한다.

### 요청한 이유
CMS-26-004, CMS-26-005에서 입력 구조가 변경되면 기존 DB 데이터가 신규 구조와 불일치한다. 기존 데이터를 신규 구조로 변환해야 서비스 일관성이 유지된다.

### 수정사항
- 기존 3-2-5 형식 사업자번호를 단일 필드 형식으로 변환
- 기존 전화번호 데이터를 확정된 표준(E.164 등)에 맞게 정리
- 마이그레이션 스크립트 작성 및 실행

### 이렇게 수정한 이유
기존 사용자가 갑자기 자신의 저장된 번호가 깨져 보이거나 재입력을 요구받으면 불신과 불편함을 느낀다. 백그라운드 마이그레이션으로 사용자가 아무것도 다시 하지 않아도 되게 함으로써 전환 경험을 투명하게 만든다.

## CMS-26-007 | 미디어그룹 운영시간 타임존 반영
> 글로벌 버전 개발 | 미디어그룹 | 우선순위: highest

### 요청사항
미디어그룹 생성/수정 시 국가/타임존을 지정하고 해당 타임존 기반으로 운영시간을 설정·표시해야 한다. DST(일광절약시간제)도 초기부터 대응한다.

### 요청한 이유
운영시간이 서버 기준(한국 시간)으로만 저장·표시되어 해외 거점 미디어그룹의 현지 실제 운영시간과 불일치가 발생한다.

### 수정사항
- 미디어그룹 생성/수정 화면에 타임존(또는 countryCode) 선택 필드 추가
- operateFromTime/operateToTime, operateDay를 지정 타임존 기준으로 저장 및 표시
- DST 구간 시간 중복/누락 처리 정책 수립 (TBD)
- 운영시간 적용 방식 확인 필요: 서버에서 타임존 계산 후 전송하는 방식인지, 안드로이드 셋탑이 현지 시간 기준으로 자체 적용하는 방식인지 확인 후 구현

### 이렇게 수정한 이유
운영자가 "오전 9시~오후 6시 운영"이라고 설정했는데 실제 현지에서 다른 시간에 켜지고 꺼진다면 설정과 실제의 불일치로 큰 혼란이 생긴다. 타임존 기반 설정은 "내가 입력한 대로 동작한다"는 예측 가능성을 보장한다.

## CMS-26-008 | IR 센서 데이터 수집 구조/API
> 글로벌 버전 개발 | 데이터 수집/분석 | 우선순위: highest

### 요청사항
IR 센서 데이터를 수집·저장하고 수집 API를 구성해야 한다.

### 요청한 이유
시청자 반응 데이터를 수집하여 광고 효과 분석에 활용하려면 IR 센서로부터 데이터를 수신·저장하는 인프라가 필요하다. 현재 수집 구조 및 API가 없어 센서 데이터 활용이 불가능하다.

### 수정사항
- IR 센서 데이터 수집 API 구성 (deviceId, sensorId, eventTime, value/count, meta 필수)
- 필수값 누락 금지, 포맷 고정(정책 수립 필요)
- 중복 적재, 비정상값, 유실 재전송 처리 정책 수립
- 운영 수집 현황/로그 화면 기획 필요 (TBD)
- 데이터 표준화 정책 및 저장/처리 용량 확보 필요

### 이렇게 수정한 이유
데이터가 수집되지 않으면 운영자가 효과 분석 화면에서 빈 화면이나 0값만 보게 된다. 수집 인프라 구축은 운영자가 의미 있는 데이터를 기반으로 결정을 내릴 수 있게 하는 UX의 전제 조건이다.

## CMS-26-009 | ColorLight LED 셋탑 전용 앱 기본 골격
> 서비스 시장 확장 | App | 우선순위: highest

### 요청사항
ColorLight LED 셋탑에서 앱 설치·실행이 가능한 기본 앱(권한/네트워크/저장소 포함)을 구축해야 한다.

### 요청한 이유
기존 앱은 Quber 셋탑 전용으로 ColorLight LED 셋탑에서 동작하지 않는다. ColorLight 하드웨어 파트너사와의 협업 및 새로운 시장 진출을 위해 전용 앱 기반이 필요하다.

### 수정사항
- ColorLight LED 셋탑 지원 OS/스펙 확보
- 권한, 네트워크, 저장소 구조를 포함한 기본 앱 골격 구축
- 설치/실행 실패 시 사용자 안내 처리
- 배포 방식(OTA 포함) 추후 확정 (TBD)

### 이렇게 수정한 이유
앱이 설치되지 않거나 실행되지 않으면 운영자는 어디서 무엇이 잘못됐는지 알 수 없다. 기본 골격 단계에서 명확한 실패 안내를 포함해야 사용자가 문제 상황에서 다음 행동을 결정할 수 있다.

## CMS-26-010 | ColorLight LED 셋탑-의존 기능 목록화
> 서비스 시장 확장 | App | 우선순위: highest

### 요청사항
기존 소스의 의존 기능을 목록화하고 동등/대체/미지원 여부를 분류하여 ColorLight 대응 범위를 확정해야 한다.

### 요청한 이유
ColorLight 앱 개발 전 기존 Quber 앱 기능 중 어떤 것이 그대로 사용 가능하고, 어떤 것이 대체가 필요하거나 지원 불가한지 파악해야 개발 일정과 리소스를 정확히 산정할 수 있다.

### 수정사항
- 기존 Quber 앱 전체 기능 목록 작성
- 각 기능에 대해 ColorLight 동등 지원 / 대체 구현 필요 / 미지원 분류
- 필수/선택 기능 구분하여 개발 우선순위 확정
- 산출물(목록 문서) 필수 제출

### 이렇게 수정한 이유
지원하지 않는 기능을 사용자가 시도했을 때 아무런 안내 없이 동작하지 않으면 "고장난 것인지 지원 안 하는 것인지"를 알 수 없다. 미지원 여부를 명확히 분류하고 UI에서 적절히 안내해야 혼란을 방지할 수 있다.

## CMS-26-011 | ColorLight LED 셋탑-콘텐츠+스케줄 재생 호환
> 서비스 시장 확장 | App | 우선순위: highest

### 요청사항
콘텐츠가 ColorLight에서 정상 재생되도록 플레이어/렌더링을 구현해야 한다. 스케줄 수신→적용→재생(순서/시간)을 지원하며 즉시반영도 포함한다.

### 요청한 이유
ColorLight LED 셋탑은 Quber와 하드웨어 구조가 달라 기존 플레이어로는 콘텐츠가 정상 재생되지 않을 수 있다. 셋탑의 핵심 기능인 콘텐츠 재생 및 스케줄 적용이 정상 동작해야 서비스 제공이 가능하다.

### 수정사항
- ColorLight 하드웨어에 맞는 플레이어/렌더링 구현
- 지원 콘텐츠 포맷 확정 (TBD) 및 유효성 검증 적용
- 스케줄 수신 → 파싱 → 순서/시간에 따라 재생하는 전체 플로우 구현
- 즉시반영 명령 수신 시 신규 스케줄로 전환

성과 데이터가 잘못된 스케줄·광고주와 연결되거나 동일 데이터가 중복 연결되는 오류가 발생한다. 광고주에게 제공하는 효과 리포트의 데이터 정확성이 낮으면 서비스 신뢰도가 훼손된다.

### 수정사항
- 연결 키 및 우선순위 기준 수립 후 매핑 로직 보완
- 매핑 실패 또는 모호한 케이스를 "미매핑/검증 필요"로 식별하는 처리 추가
- scheduleId, dateRange 기준으로 정확한 성과 데이터 연결

### 이렇게 수정한 이유
잘못 매핑된 데이터가 리포트에 표시되면 운영자는 "이 수치가 맞는 건가"를 항상 의심하게 된다. 데이터 정확성이 확보되어야 사용자가 화면을 의사결정의 근거로 신뢰하고 활용할 수 있다.

## CMS-26-024 | 효과 분석-동일 지점 미디어그룹 수동 매핑(대표 묶음)
> 서비스 고도화 | 데이터 수집/분석 | 우선순위: highest

### 요청사항
동일 지점에서 미디어그룹 다건으로 중복 유입되는 효과 데이터를 방지하기 위해 대표 묶음으로 수동 매핑하고 리포트는 1건(대표값)으로 표시해야 한다.

### 요청한 이유
동일 물리적 위치에 복수의 미디어그룹이 등록된 경우 동일 시청자 데이터가 여러 미디어그룹에 중복 집계되어 효과 수치가 부풀려진다.

### 수정사항
- mediaGroupId와 mappingGroupId를 연결하는 수동 매핑 기능 구현
- 1개 mediaGroupId는 1개 mappingGroupId에만 소속 가능
- 중복 소속/매핑 누락 처리 정책 수립
- 리포트에서 mappingGroupId 단위로 1건(대표값)으로 집계하여 표시
- 대표값 선택 기준 추후 논의 (TBD)

### 이렇게 수정한 이유
같은 지점에서 시청자 수가 2배로 집계된 리포트를 보면 운영자는 수치가 이상하다는 걸 직감하지만 원인을 찾기 어렵다. 수동 매핑으로 "1개 지점 = 1건 집계"가 되어야 운영자가 리포트 수치를 있는 그대로 신뢰할 수 있다.

## CMS-26-025 | 효과 분석-중복 집계 방지(지표 계산 규칙)
> 서비스 고도화 | 데이터 수집/분석 | 우선순위: highest

### 요청사항
동일 지점 다건 유입 시 성별/연령 등 합산이 부적절한 지표가 누적 합산되어 왜곡되지 않도록 지표별 계산 규칙을 적용해야 한다.

### 요청한 이유
성별·연령 분포 지표는 중복 집계 시 단순 합산이 통계적으로 올바르지 않아 수치가 왜곡된다. 예를 들어 동일 인물이 두 미디어그룹에 각각 집계되면 전체 시청자 수가 2배로 부풀려진다.

### 수정사항
- 지표 유형별 집계 방식 정의 (단순합산/대표값/가중평균 등)
- scheduleId, dateRange, 연동 mappingGroupId 기준으로 지표 계산 규칙 적용
- 기준 미정 지표는 집계불가/대표값 정책 적용
- 지표별 규칙 및 대표값 기준 추후 논의 (TBD)

### 이렇게 수정한 이유
부풀려진 수치를 보고 광고주에게 잘못된 효과를 보고하면 사용자와 광고주 모두의 신뢰가 한 번에 무너진다. 정확한 집계 규칙은 리포트가 "실제 현실을 반영하는 도구"로서의 가치를 유지하는 근거가 된다.

## CMS-26-028 | 효과 분석-미디어그룹 상세 효과 지표 제공

### 요청사항

### 요청한 이유

## CMS-26-029 | 수정/삭제 정책 적용(Soft/Hard Delete)
> 서비스 고도화 | 정책 | 우선순위: highest

### 요청사항
콘텐츠/스케줄/로그 수정 및 삭제 정책을 정립하고 서비스 내에서 사용자에게 수정/삭제 가이드를 제공해야 한다. Soft delete/Hard delete 구조를 설계·적용한다.

### 요청한 이유
현재 삭제 방식이 리소스 유형별로 통일되지 않아 어떤 데이터는 복구 가능하고 어떤 데이터는 영구 삭제되는지 운영자가 파악하기 어렵다. 명확한 정책이 없으면 실수로 중요 데이터가 영구 삭제될 위험이 있다.

### 수정사항
- resourceType별 삭제 방식(Soft/Hard) 정책 확정
- 권한/상태 기반 삭제 제한 규칙 적용
- 운영중/확정 상태 리소스 삭제 시 제한 안내 처리
- 참조무결성 처리 정책 수립
- 삭제/복구/감사로그 범위 확정 (TBD)
- 각 관리 화면에 삭제 가이드 표시

### 이렇게 수정한 이유
삭제 버튼을 눌렀을 때 "이게 복구 가능한가"를 알 수 없으면 사용자는 삭제 행동 자체를 두려워하게 된다. 삭제 유형과 복구 가능 여부를 화면에서 명확히 안내하면 사용자가 자신 있게 행동할 수 있고, 실수로 인한 스트레스도 줄어든다.

## CMS-26-032 | 스케줄 순서 변경-편집 모드

### 요청한 이유
현재 스케줄 목록에서 순서를 변경하면 즉시 반영되어 운영 중 실수로 순서를 바꾸면 방송 사고로 이어질 수 있다.

### 이렇게 수정한 이유
목록 화면에서 실수로 드래그하면 즉시 방송에 영향이 가는 구조는 사용자에게 항상 긴장 상태를 강요한다. 편집 모드 버튼을 명시적으로 누른 후에만 변경이 가능하게 하면 일상적인 조회와 편집 의도를 명확히 분리하여 실수 공간을 없앤다.

- deviceId, volumeLevel(범위 제한 정책 TBD)을 입력받아 셋탑에 전송
- 디바이스 선택 필수
- CMS-26-019(GW-01 명령 안정화)와 연계하여 전송 신뢰성 확보

### 이렇게 수정한 이유
볼륨 조정을 위해 현장에 전화하거나 방문해야 한다면 단순한 조작 하나를 위해 과도한 비용과 시간이 든다. 모니터링 화면 안에서 바로 볼륨을 조정할 수 있으면 운영자가 화면을 떠나지 않고 업무를 완결할 수 있어 운영 효율이 크게 높아진다.

## CMS-26-045 | 재생정보-요약/상세 분리(탭 구조)
> 서비스 고도화 | 모니터링 | 우선순위: medium

### 요청사항
미디어 모니터링 상세 화면의 재생 로그 영역을 '요약(재생 정보)'과 '상세(재생로그)'로 분리하여 제공해야 한다. 두 탭 모두 동일한 기간 필터(dateRange)를 공유한다.

### 요청한 이유
현재 재생 정보 화면에서 집계 요약과 개별 이벤트 로그가 혼재되어 사용자가 원하는 정보를 찾기 어렵다. 대부분의 사용자는 집계 요약만 필요하며, 상세 로그가 필요한 경우는 소수다.

### 수정사항
- 재생 로그 영역을 요약 탭/상세 탭으로 분리 (상단 탭 또는 토글 방식)
- 요약 탭: 콘텐츠 단위 집계(콘텐츠명/평균 재생횟수·보장횟수/평균 재생간격/최근 송출시간) 유지
- 상세 탭: 개별 재생 이벤트 단위 로그 제공 (CMS-26-046 연계)
- 두 탭에서 동일한 dateRange 필터 공유

### 이렇게 수정한 이유
집계 수치와 이벤트 로그가 한 화면에 섞여 있으면 필요한 정보를 찾는 데 시간이 걸리고 화면이 복잡해 보인다. 요약/상세 탭 분리는 "빠른 확인"과 "깊은 분석"이라는 서로 다른 사용자 목적을 각각 최적화된 화면으로 지원한다.

## CMS-26-046 | 재생로그-세부 정보 제공(이벤트 단위)
> 서비스 고도화 | 모니터링 | 우선순위: medium

### 요청사항
'재생로그(상세)' 탭에서 선택 기간 동안의 재생 이벤트를 건별로 조회 및 다운로드할 수 있어야 한다. 무한 스크롤로 탐색하며, 각 이벤트는 콘텐츠 식별 정보와 송출 시각을 포함해야 한다.

### 요청한 이유
광고 운영 검증이나 이슈 분석 시 개별 재생 이벤트 수준의 로그가 필요하지만 현재는 집계 수치만 제공된다. 건별 재생 이력 추적이 가능해야 광고 송출 보증 및 분쟁 처리가 가능하다.

### 수정사항
- 재생로그(상세) 탭에서 dateRange, mediaId/deviceId, contentId 기반 이벤트 목록 무한 스크롤 조회
- 각 이벤트에 콘텐츠 식별 정보 + 송출 시각 필수 포함
- 최대 조회 기간 제한 정책 수립
- 대용량 조회 시 로딩/부분 로딩 처리
- 데이터 없음/조회 실패 상태 처리
- 다운로드 기능 제공

### 이렇게 수정한 이유
"이 콘텐츠가 오전 10시 27분에 실제로 나갔는가"를 확인해야 하는데 집계 수치만 있다면 운영자는 근거를 제시할 수 없어 분쟁 상황에서 무력해진다. 이벤트 단위 로그는 운영자가 언제든 구체적인 근거를 화면에서 꺼낼 수 있는 신뢰의 도구가 된다.

## CMS-26-048 | 다중 선택 UX 제공
> 서비스 고도화 | 공통 리스트 | 우선순위: medium

### 요청사항
리스트 화면에서 다중 선택 후 일괄 삭제 및 복제 기능을 제공해야 한다.

### 요청한 이유
콘텐츠·스케줄·미디어 등이 많은 환경에서 개별 항목을 하나씩 처리하는 작업이 비효율적이다.

### 수정사항
- 리스트 화면에 체크박스 기반 다중 선택 UI 추가
- selectedIds 1개 이상 선택 가능
- 선택 0개 상태에서 액션 실행 제한
- 조건 미충족 대상(예: 운영중 스케줄) 선택 불가 처리

### 이렇게 수정한 이유

## CMS-26-049 | 일괄 삭제/복제 액션 제공
> 서비스 고도화 | 공통 리스트 | 우선순위: medium

### 요청사항
리스트 화면에 체크박스 기반 다중 선택 기능을 제공하여 여러 항목을 한 번에 선택하고 일괄 처리할 수 있어야 한다. 전체 선택/선택 해제, 선택 개수 표시 등 기본 UX를 포함한다.

### 요청한 이유
일괄 삭제·복제 기능을 제공하더라도 한 번에 여러 항목을 선택하는 UX가 없으면 개별 선택-처리를 반복해야 한다. 다중 선택 UX를 표준화하여 모든 리스트 화면에서 일관된 방식으로 제공해야 한다.

### 수정사항
- selectedIds, action(delete/copy) 기반 일괄 처리
- 선택 항목 1개 이상 조건 검증
- 삭제·복제 조건(운영중 등) 검증 후 처리 차단/안내
- 부분 실패 시 성공/실패 목록 구분 안내
- 삭제 불가 상태는 CMS-26-029(Soft/Hard Delete 정책)에 따라 처리

### 이렇게 수정한 이유
일부 항목 처리에 실패했을 때 어떤 항목이 됐고 어떤 항목이 안 됐는지 알 수 없으면 운영자는 전체를 다시 확인해야 한다. 성공/실패 목록을 구분하여 안내하면 운영자가 실패한 항목만 빠르게 재처리할 수 있어 후속 작업 부담이 줄어든다.

## CMS-26-050 | 대시보드 그래프 인터랙션 개선
> 서비스 고도화 | 대시보드 | 우선순위: low

### 요청사항
대시보드 그래프의 사용자 인터랙션(툴팁, 선택/강조, 드릴다운/필터 연동 등)을 개선하여 가독성과 사용성을 높여야 한다.

### 요청한 이유
현재 대시보드 그래프가 정적으로 표시되어 특정 데이터 포인트의 상세 정보를 확인하거나 그래프에서 직접 필터를 적용하는 것이 불가능하다.

### 수정사항
- 그래프 마우스오버 시 툴팁으로 상세 수치 표시
- 그래프 항목 클릭 시 해당 데이터 강조 표시
- 드릴다운 또는 필터 연동으로 관련 상세 화면으로 이동 가능
- 대시보드 > 그래프 전 영역에 적용

### 이렇게 수정한 이유
정적인 그래프는 "전체적인 추이"는 보여주지만 특정 날짜의 수치가 궁금할 때 그래프 밖에서 따로 찾아야 한다. 툴팁과 드릴다운은 그래프 위에서 바로 궁금한 점을 해소할 수 있게 해 화면 이탈 없이 탐색이 완결되도록 한다.

## CMS-26-051 | 플로팅 버튼 제공 로직 개선
> 서비스 고도화 | 공통 | 우선순위: low

### 요청사항
플로팅 버튼 노출/비노출 조건과 동작 로직을 개선하여 화면 상태에 따라 일관되게 제공되어야 한다(중복 노출/오작동 방지).

### 요청한 이유
플로팅 버튼이 화면 상태와 무관하게 노출되거나 중복으로 표시되는 등 일관되지 않은 동작이 보고되었다. 잘못된 컨텍스트에서 노출되면 의도하지 않은 액션이 실행될 수 있다.

### 수정사항
- 페이지/권한/스크롤/상태 기반 노출 조건 정의
- 노출 조건 및 버튼 액션 정의 완료 후 구현
- 중복 노출 방지 로직 추가
- 대시보드/공통 영역 전반에 적용

### 이렇게 수정한 이유
플로팅 버튼이 의도치 않은 화면에서 보이거나 중복으로 나타나면 "이 버튼을 눌러야 하나"라는 혼란과 잘못된 클릭 위험이 생긴다. 일관된 노출 조건은 사용자가 "이 버튼이 보이면 지금 사용할 수 있다"는 신뢰를 형성하게 하여 화면과 사용자 간의 예측 가능한 관계를 만든다.
